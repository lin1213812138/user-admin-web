# 打包部署后访问报 404（Failed to load resource）

## 现象

部署后浏览器控制台报错：

- 首条无文件名的 `404`（即入口脚本 `index-BvyQGzSu.js`）
- `chunk-jRWAZmH_.js` / `preload-helper-033FLyyK.js` / `vue.runtime.esm-bundler-DJSF7irw.js` / `theme-Bj98q6Ln.js` / `exceljs.min-DtYphSaB.js`
- `index-CaSJxEOt.css` / `theme-TXYm1Ny7.css`
- 其余 `chrome-extension://...` 与 `manifest.json` 报错是浏览器插件（截图/翻译类扩展）自身噪音，与本次无关。

## 定位过程

1. 报错中的 7 个文件名与本地 `dist/index.html`（`buildTime=2026-09-15 19:31:07`）中的引用**完全一致** →
   部署的就是这份产物，**构建与上传内容本身没有问题**，问题在「请求路径」。
2. `dist/index.html` 内所有资源都是**站点根路径的绝对引用**（`/assets/xxx.js`、`/assets/xxx.css`）：
   - `vite.config.ts`：`base: viteEnv.VITE_BASE_URL`
   - `.env`：`VITE_BASE_URL=/`；`.env.prod` 未覆盖该变量（prod 构建同样是 `/`）
   - `src/router/index.ts`：`createWebHistory(VITE_BASE_URL)`，路由 base 同为 `/`
3. 控制台里页面自身的来源标识是 `tms-user:1`，说明**访问地址最后一段是 `/tms-user/`**，即应用部署在**子路径**下。
4. 结论：浏览器按 `/assets/...` 去站点根目录取文件（`http://<host>/assets/xxx.js`），而文件实际位于
   `http://<host>/tms-user/assets/xxx.js` → 全部 404。
   同类表现的另一可能：服务器上只上传了 `index.html`，`assets/` 目录未部署。

## 快速验证（10 秒）

DevTools → Network → 点开任一失败请求看 **Request URL**；或直接在地址栏访问：

- `http://<host>/assets/index-BvyQGzSu.js`
- `http://<host>/tms-user/assets/index-BvyQGzSu.js`

哪个返回 200，文件就在哪个路径下。

## 可选修复

- **A. 部署到域名根目录（无需改代码、无需重新构建，优先）**
  把 `dist/` 内的 `index.html`、`assets/`、`favicon.svg`、`logo.png` 放到站点 root，用 `http://host/` 访问。
  history 模式下静态服务器必须做 fallback：`try_files $uri $uri/ /index.html;`，否则刷新子路由仍会 404。

- **B. 保留子路径 `/tms-user/`（必须挂子路径时）**
  在 `.env.prod` 增加 `VITE_BASE_URL=/tms-user/`（**必须以 `/` 结尾**）→ `pnpm build` → 重新上传整个 `dist/`。
  路由 base 自动跟随（同一变量）；`index.html` 里的 `/favicon.svg` 等 public 资源由 Vite 自动加上 base 前缀。
  服务器侧同样需要：`/tms-user/assets/*` 能映射到实际目录 + history fallback 到 `/tms-user/index.html`。
  注意 `VITE_SERVICE_BASE_URL` 是绝对地址（`http://124.71.223.164:10010`），不受 base 影响，但要求浏览器可直连该地址且后端放行 CORS。

- **C. `base: './'` 相对路径**
  不推荐：history 模式下 `createWebHistory` 无法使用相对 base，深链刷新会更糟。

- **D. 保留子路径 + 改 hash 路由模式（后端不便改动时的兜底）**
  `.env.prod` 设 `VITE_BASE_URL=/tms-user/`，并把 `VITE_ROUTER_HISTORY_MODE` 改为 `hash` → URL 形如 `/tms-user/#/home`，
  不依赖服务器任何 fallback，刷新/直达任意页面均正常；代价是地址带 `#`、观感略差。

## 实测确认（2026-09-15，HEAD 探测 `http://124.71.223.164:10010`）

| 请求                                                                | 结果                                                                      |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `/tms-user`                                                         | 200 text/html 1039B（**不重定向**，直接返回 index.html）                  |
| `/tms-user/`                                                        | 200 text/html 1039B                                                       |
| `/tms-user/index.html`                                              | 200 text/html 1039B（与本地 `dist/index.html` 一致）                      |
| `/tms-user/assets/index-BvyQGzSu.js`                                | 200 application/javascript 1626808B                                       |
| `/assets/index-BvyQGzSu.js`                                         | **404**                                                                   |
| `/tms-user/favicon.svg`                                             | 200 image/svg+xml                                                         |
| `/tms-user/home`、`/tms-user/login`、`/tms-user/no-such-route-test` | **404**（后端未做 SPA history 回退）                                      |
| `/api/v1/user/session/get`                                          | 404 —— 属正常，该接口后端仅注册 POST（见 `src/service/api/auth.ts` 注释） |

结论：**产物已完整部署在 `/tms-user/` 下，唯一问题是资源前缀 base 不匹配**；
另外查出一个连带问题：后端未做 history 回退，修好 base 后「刷新/直达子路由」仍会 404，需要一并处理。

## 改动计划（待用户确认）

前端（本仓库）：

1. `.env.prod` 新增 `VITE_BASE_URL=/tms-user/`（**必须以 `/` 结尾**）。
2. `pnpm build` 重新构建 → 产物内资源引用变为 `/tms-user/assets/*`，favicon 自动带前缀。
3. 整体替换服务器 `/tms-user/` 目录内容（`index.html` + `assets/` + `favicon.svg`）。
4. 不改 `vite.config.ts`、`src/router/index.ts`（同一个 `VITE_BASE_URL` 自动驱动 base）。
5. 不改 `VITE_SERVICE_BASE_URL`（绝对地址、同源同端口，与 base 无关）。

后端（不在本仓库，需协调）：

6. `/tms-user/*` 未命中静态文件时回退 `index.html`（history fallback）；否则刷新子路由 404。
7. `/tms-user`（无尾斜杠）建议 301 → `/tms-user/`：`createWebHistory('/tms-user/')` 的 stripBase 要求路径以 `/tms-user/` 开头，
   否则会把 `/tms-user` 当成业务路由 → 渲染 404 页。

## 决策点（待用户确认）

- ① history fallback 由后端补，还是前端改用 hash 模式（方案 D）？
- ② `pnpm build:test`（`--mode test`）的产物是否也要部署到 `/tms-user/`？
  若是，`.env.test` 也需设 `VITE_BASE_URL=/tms-user/`，代价是 `pnpm dev` 本地地址变成 `http://localhost:9111/tms-user/`。

## 后续：如果部署路径再变化

关键事实（已实测，2026-09-15）：Vite 加载 env 时**进程环境变量优先级高于 `.env*` 文件**——
shell 内设 `VITE_BASE_URL=/临时覆盖测试/` 后 `loadEnv('prod', cwd)` 解析结果即该值。
因此换部署路径无需改任何文件：

```powershell
$env:VITE_BASE_URL="/新路径/"; pnpm build   # 结尾必须带 /
```

组织方式的候选（待用户选择）：

- **A（当前采用）** `.env.prod` / `.env.test` 存线上默认值，换目标时用 shell 变量临时覆盖。改动最少，代价是裸跑 `pnpm build` 会落到默认值。
- **B（多部署目标）** 把 base 从 `.env.prod` 撤掉，按目标拆 `.env.<mode>`（如 `.env.tms-user`）+ `"build:xxx": "vite build --mode xxx"`；注意 mode 名同时决定其它变量（如 `VITE_SERVICE_BASE_URL`）从哪个文件读取。
- **C（换路径免重新构建）** `base: './'` 相对路径 + hash 路由：资源相对 index.html 解析，任意子目录都能跑且不需要服务器 fallback；代价是 URL 带 `#`，且 history 模式无法使用相对 base。
- **D（治本）** 让后端把前端挂到根目录，或用反向代理去掉路径前缀，前端 base 恒为 `/`。

注意：只要使用绝对 base（A / B / D 的前半段），**换路径必然要重新构建 + 重新上传**，因为 base 会被写进 `index.html` 与 vue-router 的 history base。

## 验证方式（部署后）

- 浏览器 Network 面板：`index-*.js`、`theme-*.css` 等资源全部 200。
- 直接访问/刷新深层路由（如 `/tms-user/home`）——当前仍会 404，待后端补 history 回退后复验。
