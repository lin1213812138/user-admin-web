# 客户等级管理界面

## 需求来源

用户提供 `tms-user` 的 `CustomerLevelSchema` 与一张客户等级列表示意图，要求在前端「客户管理」菜单下新增一个管理界面。

## 已确认信息

- 后端 `tms-user/lib/api-v1-web/customer-level/customer-level.js` 已提供完整 CRUD：
  - `POST /customer-level/create`
  - `POST /customer-level/update`
  - `POST /customer-level/delete`
  - `POST /customer-level/query`
  - `POST /customer-level/get`
- 服务层 `tms-user/lib/services/customer-level.js` 关键行为：
  - `name` 为唯一字段；
  - `num`（等级序号）由后端在 `create/update/delete` 后自动重排（`updateNum`）；
  - `delete` 会校验是否被客户引用（`customerService.isExist({ levelId })`），若存在关联客户则抛出 `DEL_ERROR`；
  - `query` 固定 `sort: { num: 1 }`，`keywordFields: ['name']`，并额外返回 `customerCount`（关联客户数）；
  - 创建/更新时间、创建人/编辑人由后端维护。
- 前端现状：
  - `src/service/api/customer/index.ts` 已有 `fetchGetCustomerLevelList`（字典接口，只查启用项），但缺少管理页专用的完整 CRUD 服务；
  - `src/typings/api/system-manage/index.d.ts` 中 `CustomerLevelItem` 只有 `_id/name/num/status/createDate/updateDate`，缺少 `limitDays/limitFeeSpent/feeShipRate/customerCount/creator/updateBy` 等字段；
  - 客户管理菜单下目前只有「客户列表」一个子菜单。

## 设计决策（待用户确认 spec）

- 新增子菜单「客户等级」，路径 `/customer-manage/customer-level`，挂在「客户管理」下，排序在「客户列表」之后；
- 参考「客户列表」与「站点/组别」管理页模式，使用 `useVxeTable` + `Table` 组件；
- 搜索框仅按名称（`name`）模糊搜索，与后端 `keywordFields` 对齐；
- 表格列与截图保持一致：客户等级（`num`）、等级名称（`name`）、期限时间（`limitDays`）、消费金额满（`limitFeeSpent`）、运费折扣（`feeShipRate`）、状态（`status`）、编辑人（`updateBy`）、编辑时间（`updateDate`）、操作；
- 状态列使用 `NSwitch`，列表直接切换启用/禁用，调用 `/customer-level/update` 局部更新（需随行回传 `name` 以避 `uniqField` 脏字段坑）；
- 新增/编辑共用抽屉，表单字段：`name`（必填）、`limitDays`、`limitFeeSpent`、`feeShipRate`、`status`；
  - `num` 由后端自动排序，前端不填；
  - `limitDays`/`limitFeeSpent` 默认 `0`；`feeShipRate` 默认 `100`；
- 操作列提供「编辑」；删除按钮可保留但受权限控制（默认启用），删除时后端会拦截有关联客户的等级；
- 导出按钮：截图有导出，但后端无专用导出接口，spec 中列为开放问题。

## 待确认问题

1. 导出按钮是否需要？如需要，后端需新增 `/customer-level/export`，否则前端仅做占位；
2. 删除按钮是否开放？后端已支持但有引用校验；
3. 是否需要在表格展示「关联客户数（`customerCount`）」一列？后端 `query` 已返回；
4. 状态列是否严格按截图使用开关，还是使用下拉选择？

## 新增弹窗截图反馈（2026-09-20）

用户提供新增等级弹窗截图，与当前实现存在以下差异，待确认修改方向：

1. 截图有两个输入框：**「客户等级」** + **「等级别名」**（必填）；当前抽屉只有「等级名称」一项必填。
2. 截图中**「运费折扣」**必填；当前非必填。
3. 截图中**「状态」**是下拉选择；当前列表与抽屉均使用开关（与第一张列表截图一致）。
4. 截图字段带单位：**天 / ¥ / %**；当前未显示单位。
5. 截图弹窗标题为**「新增等级」**；当前用通用 `common.add`/`common.edit`。
6. 若截图中的「客户等级」对应 Schema 的 `num` 字段，则与后端当前「create/update/delete 后自动重排 num」逻辑冲突，需确认是否改为允许前端手动指定 num。

## 新增弹窗确认与调整（已实施）

- 用户确认全部按截图修改：①「客户等级」= Schema `num`（允许手动输入，但后端当前 `updateNum` 会自动重排覆盖，已标注风险）；②「等级别名」= `name`（必填）；③ 状态改下拉选择（启用/停用，列表仍保留开关）；④ 运费折扣必填；⑤ 字段单位（天/¥/%）加在 label；
- 抽屉 `customer-level-operate-drawer.vue` 已重写为 2 列布局：`num`(客户等级)/`name`(等级别名,必填)/`limitDays`(期限时间(天))/`limitFeeSpent`(消费金额满(¥))/`feeShipRate`(运费折扣(%),必填)/`status`(下拉)；标题改为「新增等级」/「编辑等级」；同时修复原 `isCreate` 判断反了的 bug；
- 国际化 `customerLevelManage` 新增 `add/edit/numPlaceholder/alias/limitDaysWithUnit/limitFeeSpentWithUnit/feeShipRateWithUnit`；`Schema` 同步；
- 类型 `CustomerLevelSaveParams` 增加可选 `num`。

## 待确认（后端风险）

- 后端 `services/customer-level.js` 的 `create/update/delete` 后调用 `updateNum()` 会把所有文档的 `num` 重新排序为 1,2,3...。若需让前端手动指定的「客户等级」生效，需调整后端：去掉自动重排或按传入 num 排序。当前前端已支持传入，实际效果以后端为准。
