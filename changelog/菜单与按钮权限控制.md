# 菜单与按钮权限控制

日期：2026-09-18
类型：设计讨论 + 实施完成
Spec：`docs/superpowers/specs/2026-09-18-permission-control-design.md`

## 问题

用户问「现在要进行菜单权限和按钮权限的控制应该怎么处理」。

## 现状定位（调研结论）

权限链路**只写不读**：角色管理页能把权限码写进 `role.auths`（`/role/auths/update`），后端 `authMap` 能对接口 403，但前端从未消费这些码。

1. **菜单过滤空转**：`src/router/elegant/routes.ts` 无任何路由声明 `meta.roles` ⇒ `filterAuthRoutesByRoles`（`store/modules/route/shared.ts:12-43`）因 `isEmptyRoles` 恒 true 原样返回；`router/guard/route.ts:29-32` 的 `hasAuth` 同样恒 true。
2. **权限码语义混装**：`role.auths` 里混了「前端自增数字菜单 id（`"601"`）」+「按钮码 `system:user:add`」+「子模块码」，后端 `authMap = zipObject(auths, true)`（`lib/services/role.js:69`）对 `601` 只当无意义 key；`userInfo.buttons === userInfo.roles`（后端不返回 `showOps`）⇒ 无法区分菜单可见与按钮可用。
3. **超管恒 false**：`isStaticSuper` 依赖 `R_SUPER`，永不出现在 `authMap`。
4. **按钮权限完全缺失**：无 `src/directives`、无 `app.directive`、`useAuth().hasAuth` 零调用、`views/system-manage/user/index.vue` 5 个 `NButton` 全裸露。

后端事实：无 menu 表 / 无 permission 表 / `system:` 前缀 0 命中 / `/route/getUserRoutes` 不存在（模板死代码）；`user.roleType` 由 `lib/services/role.js:77` 注入会话（`max(map(roleList,'roleType'))`），`ADMIN=100`（`lib/common/define/1002-role.js`）。

## 决策（澄清 4 问 + 1 次补充）

| 决策点       | 结论                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 菜单权限来源 | **静态路由 + meta 权限码过滤**（沿用 elegant-router，不改后端、不启用 dynamic 模式）                                                                |
| 数字菜单 id  | **废弃**，统一 `system:xxx` 码；读取时只认带 `:` 的 key（逻辑废弃，不迁移 DB 脏数据）                                                               |
| 按钮用法     | **`v-auth` 指令 + `useAuth().hasAuth` 两者都提供**                                                                                                  |
| 超管         | **`roleType===100`**（与后端 `ADMIN=100` 对齐，用户最终确认；统一引用常量 `SUPER_ROLE_TYPE`）+ 保留 `accountType===1`（后端 `auth.js:22` 直通口径） |
| 后端         | **零改动**（用户明确）                                                                                                                              |

## 方案要点

- **认证层**：`applyUser()` 派生 `userInfo.permissions`（过滤 `authMap` 中含 `:` 的 key），移除语义混乱的 `roles`/`buttons`；`isStaticSuper` → `isSuperAdmin = roleType === SUPER_ROLE_TYPE(=100) || accountType === 1`（修掉恒 false 的老 bug，已与后端 ADMIN 对齐）。
- **菜单**：`build/plugins/router.ts` 的 `onRouteMetaGen` 是 meta 唯一注入点（icon/order/hideInMenu 都在此），新增 `routePermissions` 映射写 `meta.permission`，**不动任何 `.vue`**；过滤函数改名 `filterAuthRoutesByPermission`，父级目录在子级被裁光后一并隐藏（现有实现会留空目录）；**未声明 permission 默认放行 + dev 告警**（避免漏配导致菜单集体消失，也保护 `VITE_ROUTE_HOME=home`）。
- **按钮**：新增 `src/directives/auth.ts`（无权限 `el.remove()`）+ `src/plugins/directive.ts` 注册；`useAuth().hasAuth` 用于 `disabled`/列渲染等逻辑判断场景；`views/system-manage/user/index.vue` 打样 5 个按钮。
- **超管「分配权限」按钮禁用**（与历史一致，`row.roleType===100` 不可点击）：超管角色 `auths` 不经由前端分配页填充，其放行依赖前端 `isSuperAdmin` 直通 + 后端 `accountType===1` 直通（或后端对 `roleType=100` 自动给全权限）；抽屉内 `isSuperRole` 强制全选只读逻辑仍保留，仅超管可打开抽屉时生效。
- **RoleType 已与后端对齐为 `100`**：`Api.SystemManage.RoleType` 与下拉「管理员」均为 `100`，与后端 `ADMIN=100` 一致；`role-operate-drawer.vue` 原下拉值为 `5` 需改成 `100`；超管判定统一引用常量 `SUPER_ROLE_TYPE`，不散落字面量。
- **仍必需的兜底**：前端 `roleType=100` 虽与后端 `ADMIN=100` 对齐，但接口层 `auth.js:22` 只认 `accountType==1` ⇒ 「管理员角色权限树强制全选只读」仍为必需，否则 `roleType=100` 但 `accountType≠1` 的超管会菜单能进、接口 403。

## 实施完成（2026-09-18）

已按设计落地并通过 `pnpm typecheck` + `pnpm lint` + `pnpm build:test`（`meta.permission` 已注入生成的 `src/router/elegant/routes.ts`，18 条业务路由全覆盖）。

**改动文件清单**

- `src/constants/auth.ts`（新增）：`SUPER_ROLE_TYPE = 100`
- `src/typings/api/auth.d.ts`：UserDetail 补 `roleType`；UserInfo 用 `permissions` 替换 `roles`/`buttons`
- `src/typings/router.d.ts`：RouteMeta 补 `permission?: string`
- `src/store/modules/auth/index.ts`：`isStaticSuper`→`isSuperAdmin`；`applyUser` 派生 `permissions`（只认带 `:` 的码）
- `build/plugins/router.ts`：`onRouteMetaGen` 注入 `routePermissions` 映射 → `meta.permission`
- `src/constants/menu-permissions.ts`：所有业务菜单补 `permission` 字段（与 router 映射一致）
- `src/store/modules/route/shared.ts`：`filterAuthRoutesByRoles`→`filterAuthRoutesByPermission`（父级子级裁光后隐藏）
- `src/store/modules/route/index.ts`、`src/router/guard/route.ts`：改用 `isSuperAdmin` + `permissions`
- `src/directives/auth.ts`（新增）+ `src/plugins/directive.ts`（新增）+ `src/plugins/index.ts` + `src/main.ts`：`v-auth` 注册
- `src/hooks/business/auth.ts`：`hasAuth` 用 `permissions` 且超管短路
- `src/views/system-manage/role/modules/role-permission-drawer.vue`：回显/提交只认 `system:` 码；`roleType===100` 时 `isSuperRole` 强制全选只读（超管分配权限按钮禁用后不会触发，逻辑保留以备可打开场景）
- `src/views/system-manage/role/index.vue`：超管「分配权限」按钮禁用（与历史一致）；新增/编辑/删除按钮加 `v-auth`
- `src/views/system-manage/user/index.vue`：新增/批量删除/编辑/启用停用/删除/导出按钮加 `v-auth`（样板）

**注意事项**

- 老角色（原 `auths` 只存数字菜单 id）登录后看不到任何业务菜单，需业务侧重新在角色管理页勾一次权限（数字 id 前端读取时自动丢弃，无害）。
- 未声明 `permission` 的路由默认放行（dev 下 console.warn），非隐藏。
- 后续其它业务页面按钮可照 `user/index.vue` 样板用 `v-auth="'system:{模块}:{动作}'"` 接入。
