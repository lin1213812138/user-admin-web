# 标签设计器拖动卡顿优化

> 日期：2026-09-12
> 状态：**已实施（2026-09-12），待手测**

## 问题

手写标签设计界面（`src/views/system-manage/label-designer/`），拖动元素改变位置时非常卡顿，用户问有没有办法"永远不卡顿"。

## 根因定位

拖动链路：`pointermove` → `store.updateElement()` → Pinia 响应式 → `design-canvas.vue` 组件级重渲染 → `property-panel.vue` geo watch → `FormWrap`/`NInputNumber` 更新 → DOM `left/top` 更新。

按影响排序：

1. **pointermove 无 rAF 合帧（主因）**：`use-canvas-interaction.ts` 在 `window` 上裸监听 `pointermove`，每个事件都是独立的事件循环 tick，Vue 调度器无法跨 tick 合并。高回报率鼠标（125~1000Hz）下每个事件都触发一次完整渲染，远超显示器 60Hz 的需要。
2. **每帧 `getBoundingClientRect()`**：`mmPerPx()` 在每次 move 中实时计算，强制同步 layout（reflow）。
3. **定位用 `left/top`**：触发 reflow；纸张容器带 `transform: scale() + box-shadow + 1mm 渐变网格背景`，重绘面积大。
4. **属性面板逐帧回写循环**：store 变化 → geo watch → `model` 更新 → `NInputNumber` 每帧变数字。

## 方案对比（已决策：A）

| 方案          | 内容                                                               | 效果                            | 结论                   |
| ------------- | ------------------------------------------------------------------ | ------------------------------- | ---------------------- |
| **A（选定）** | 拖动期脱离响应式：move/resize 只直写 DOM，pointerup 一次写回 store | 拖动帧内仅 GPU 合成，60fps 稳定 | ✅ 用户确认            |
| B（保守）     | 仅 rAF 合帧 + 缓存 mpp                                             | 明显缓解，每帧仍走响应式        | 备选                   |
| C（终极）     | Canvas/WebGL 引擎重写                                              | 上限数万元素                    | 对标签场景过度设计，否 |

关于"永远不卡顿"：无绝对上限方案，但标签规模（几十个元素）下方案 A 等效无卡顿。

## 最终设计（方案 A 详细版）

### 核心思路

拖动/缩放期间 **store 完全不动、Vue 完全不渲染**，只直接操作被拖元素的 DOM；松手时一次性算好最终几何写回 store。属性面板拖动中数字不动，松手后由现有 geo watch 自动同步一次（用户已确认「拖动结束后同步」），**`property-panel.vue` 零改动**。

### 改动文件（仅 2 个）

- `src/views/system-manage/label-designer/modules/use-canvas-interaction.ts` — 核心重构
- `src/views/system-manage/label-designer/modules/design-canvas.vue` — 元素节点加 `:data-id="el.id"`；平移容器加 `ref="panRef"`

### 交互生命周期

**pointerdown（begin）**：

- 记录 `startX/Y`、`orig 几何 {x,y,width,height}`；缓存 `mmPerPx`（只调一次 `getBoundingClientRect()`）
- `paperEl.querySelector('[data-id="<id>"]')` 拿被拖元素 DOM 引用；拖动中给它加 `will-change: transform`（独立合成层，避免整纸重绘）

**pointermove（rAF 合帧）**：

- 事件回调只存最新 `clientX/clientY`，已有 pending rAF 则跳过；每帧最多执行一次：
- 算目标几何（mm，**含边界钳制**：move ≥ 0、resize ≥ 2mm，与现有行为一致）→ 换算本地 px → 直写 DOM：
  - move：`dom.style.transform = translate(dx, dy)`
  - resize：直写 `width/height`（n/w handle 加 `left/top`）
- **不碰 store** → 零响应式、零 vnode diff、零属性面板更新

**pointerup**：

- 取消 pending rAF；清直写的 inline 样式与 `will-change`
- 若真实拖动（累计位移 > 0.2mm）：`store.snapshot()`（此时 store 仍是拖动前状态）→ `store.updateElement(最终几何)`
- 未拖动：不产生撤销点
- 移除 window 监听

### 顺带修正（同一交互路径内的产物，用户已确认）

- 点击不拖不再产生撤销点（原 begin 即 snapshot；改为 moved 才记录）
- 画布空白平移（pan）同样 rAF 合帧直写 DOM，松手写回 `pan.value`

### 不做的事（YAGNI）

不加吸附/对齐线；不动 store 结构与 undo/redo 数据流；不动 `ElementRenderer` / `property-panel.vue`；不引入新依赖。

### 换算一致性

`mpp = mm/屏幕px = w / rect.width`（rect 已含 zoom），即 `mpp = 1 / (PX_PER_MM × zoom)`。实现用 `本地px = (final_mm - orig_mm) × PX_PER_MM` 直写，与设计稿的 `屏幕位移 ÷ zoom` 数学等价。

## 实施结果

### 追加：属性面板实时同步（2026-09-12 第二轮）

用户反馈拖动中 X/Y/宽/高 需实时更新且不能卡顿。方案：**拖动预览通道**（独立轻量响应式源）。

- `store/modules/label-design/index.ts`：新增 `dragPreview` ref（`Geometry | null`）——仅显示用，不进 elements/撤销/toJson。
- `use-canvas-interaction.ts`：`applyFrame`（rAF 合帧）直写 DOM 的同时写 `store.dragPreview`；`onPointerUp` 置 `null`。
- `property-panel.vue`：geo watch 源优先消费 `dragPreview`（为空回落 `selected`），复用现有 rAF 节流 + `syncing` 防回写。
- 不卡顿原理：画布模板不依赖 `dragPreview` → 拖动帧画布渲染仍为零；每帧唯一响应式更新是面板 4 个 NInputNumber 显示值（组件局部，~0.5ms）。备用保险（未启用）：面板数字可降 30Hz。

### 第一轮：拖动性能重构

- `use-canvas-interaction.ts` 全量重构：`drag` 改普通变量（脱离响应式）；begin 缓存 `mmPerPx`、查 DOM 引用、加 `will-change`；pointermove 只存坐标 + rAF 合帧（`applyFrame` 直写样式）；pointerup 清直写键、真实拖动才 `snapshot()` + `updateElement()`。
- `design-canvas.vue`：元素加 `:data-id`；pan 改 rAF 合帧直写 `panRef` 容器 transform，`onPanUp` 写回 `pan.value`（与拖拽同策略）。
- 验证：两个改动文件 typecheck / lint / oxfmt 全部通过。仓库当时存在两处**与本任务无关的失败**（均为用户并行编辑「关联标题」功能的中间态）：`locales/langs/*.ts` 缺 labelDesign 的 14 个键（typecheck 报错）；`property-panel.vue` / `element-renderer.vue` 的 lint 错误随用户实时保存而变化（两次 lint 报错内容不同即为证据）。按「只改用户明确要求的代码」原则未越界代修。
